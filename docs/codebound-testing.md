# Set up and test Codebound locally

Use this guide to verify saving, opening, running, editing, and deleting a
Codebound script. The walkthrough uses a small local API with predictable data.
If `setup_demo_get_post` already works in your connector, you can reuse it and
skip the local fixture and connector creation steps.

Use the checkout or branch containing the Codebound changes, including migration
`20261017000000_add_codebound_scripts`. The commands use your current checkout
path; replace it if testing on another machine.

## 1. Prepare the application

You need Node.js **22.12 or newer**, npm **9 or newer**, and Docker with Compose.
Start Docker Desktop before the database commands.

For a **new installation only**, run `./setup.sh` from the repository root first.
Choose **Local development**, **localhost**, and PostgreSQL port **5433**. Let it
create `.env`, install dependencies, start PostgreSQL, and generate Prisma.
Continue with the commands below. Keep `.env` uncommitted.

For **your existing installation**, keep the current `.env`. From the repository
root, start PostgreSQL:

```bash
cd /Users/gone_snow/anythingmcp
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres
```

If dependencies are missing or have changed since your last installation, run
`npm ci` from that same directory. This installs the locked QuickJS dependency
used by the script runner.

Apply migrations and generate the Prisma client:

```bash
cd /Users/gone_snow/anythingmcp/packages/backend
set -a
. ../../.env
set +a
npx prisma migrate deploy
npx prisma generate
```

The local `DATABASE_URL` must point to `localhost:5433`, using the credentials
generated by setup. Do not replace your working secrets with example values.
The migration `20261017000000_add_codebound_scripts` should be applied, or Prisma
should report that no pending migrations remain.

Do not rerun setup over your existing configuration just to test this feature.

## 2. Start the local demo API

Skip this step if you already have a working `setup_demo_get_post` tool.

In a separate terminal, run this Node script and leave it running:

```bash
node --input-type=module <<'JS'
import { createServer } from 'node:http';

createServer((request, response) => {
  response.setHeader('Content-Type', 'application/json');
  if (request.method !== 'GET' || request.url !== '/posts/1') {
    response.writeHead(404);
    response.end(JSON.stringify({ error: 'Not found' }));
    return;
  }
  response.end(JSON.stringify({
    id: 1,
    title: 'Codebound demo post',
    body: 'This intermediate field should not appear in the script result.',
  }));
}).listen(4100, '127.0.0.1', () => {
  process.stdout.write('Demo API ready at http://127.0.0.1:4100/posts/1\n');
});
JS
```

Paste the entire block, including the first and last lines. The command stays
running while the API listens. Keep this terminal open until testing is finished.

In another terminal, check it:

```bash
curl --fail http://127.0.0.1:4100/posts/1
```

Expected response:

```json
{
  "id": 1,
  "title": "Codebound demo post",
  "body": "This intermediate field should not appear in the script result."
}
```

For this local fixture, the connector needs permission to reach loopback. In
the repository-root `.env`, add `127.0.0.1` to `SSRF_ALLOWED_HOSTS`. If the setting
does not exist, add:

```dotenv
SSRF_ALLOWED_HOSTS=127.0.0.1
```

Keep any existing hosts in that comma-separated list. Restart the application
after editing `.env`. This lets the trusted connector reach your demo API;
scripts themselves still have no direct network access.

## 3. Start the application and sign in

In an application terminal:

```bash
cd /Users/gone_snow/anythingmcp
npm run dev
```

Keep that terminal open. The frontend runs at [localhost:3000](http://localhost:3000)
and the backend at [localhost:4000](http://localhost:4000).

Sign in with your existing account. For a new installation, register the first
account to become administrator. If the sign-up screen requests email
verification, configure working SMTP through setup and complete verification;
the local fixture itself needs no external API account.

Use an **administrator or editor** for the save/edit/delete walkthrough.

## 4. Add the demo connector and assign it to a server

Skip connector creation if your existing demo tool already works.

1. Open **Build → Connectors** and create a **REST API** connector.
2. Set the connector name to `Codebound Demo`, Base URL to
   `http://127.0.0.1:4100`, and Authentication to **None**. Leave the optional
   OpenAPI specification URL empty. Click **Create connector**.
3. On its detail page, choose **Import Tools → JSON Definition**. Paste the
   following array, then click **Import**:

```json
[
  {
    "name": "setup_demo_get_post",
    "description": "Read the fixed local demo post for Codebound testing.",
    "parameters": {
      "type": "object",
      "properties": {},
      "additionalProperties": false
    },
    "endpointMapping": {
      "method": "GET",
      "path": "/posts/1"
    },
    "outputSchema": {
      "type": "object",
      "properties": {
        "id": { "type": "integer" },
        "title": { "type": "string" },
        "body": { "type": "string" }
      },
      "required": ["id", "title", "body"]
    }
  }
]
```

4. Make sure the connector is active and the imported tool is enabled. Expand
   the tool's test panel and use **Run Test** with `{}`. It should return the
   post above. Resolve connector errors here before testing a script.
5. Open **Build → MCP Servers**. Use an existing active server, or choose
   **New MCP Server**, name it `Codebound Demo`, and click **Create**.
6. Open that server and tick `Codebound Demo` under **Assigned connectors**.
   Assignments save immediately; wait for **Saved**. If a connector assignment
   dialog appeared earlier, you can use it instead of assigning twice.

Codebound currently lists permitted REST `GET`, `HEAD`, and `static` tools. A
write tool or a tool from an unassigned connector will not appear.

## 5. Run and save your first script

Open **Build → Codebound**, or visit
[localhost:3000/codebound](http://localhost:3000/codebound).

1. Choose the MCP server containing your demo connector.
2. Check `setup_demo_get_post` under **Allowed tools for this script**.
3. Set **Script name** to `Post summary` and **Description** to
   `Return the post ID and title, with optional uppercase output`.
4. Paste this into **JavaScript**:

```javascript
const post = await tools.call('setup_demo_get_post', {});
if (!post || typeof post.id !== 'number' || typeof post.title !== 'string') {
  throw new Error('Expected a post with a numeric id and a title.');
}
return {
  id: post.id,
  title: input.uppercase ? post.title.toUpperCase() : post.title,
};
```

5. Set **Parameters (JSON)** to:

```json
{ "uppercase": false }
```

6. Click **Run script**. With the local fixture, expect:

```json
{ "id": 1, "title": "Codebound demo post" }
```

The result should show **1 tool calls**. The API's `body` field should be absent
from the final result. An existing demo connector may return a different title.

7. Click **Save script**. Expect **Script saved.** and an **Open** button for
   `Post summary` in the saved-script list.

## 6. Check the saved-script lifecycle

| Action | Expected result |
| --- | --- |
| Refresh the browser, then click **Open** for `Post summary` | Name, description, source, tool allowlist, and default parameters are restored. |
| Click **Run script** without changing source | The saved script returns the same compact result. |
| Change parameters to `{ "uppercase": true }` and run | Title becomes `CODEBOUND DEMO POST`; the stored defaults stay unchanged until you save. |
| Open the script again; accept discarding unsaved edits if prompted | The saved default `{ "uppercase": false }` returns. |
| Add `source: 'saved-script'` to the returned object, then click **Save changes** | The saved version is updated. Reload, open, and run: the result includes `source`. |
| Stop the application with Ctrl+C, run `npm run dev` again, reload, and open the script | It remains saved in PostgreSQL. Keep the fixture terminal running for connector calls. |
| Click **Delete** for the script, then **Confirm delete** | The saved entry disappears. Refreshing does not bring it back. |

Delete only your test script. Deleting an MCP server also deletes its linked
scripts, so keep the server while testing persistence.

To check concurrent editing, save a script and open it in **two browser tabs**.
In tab A, change its description and save. In tab B, change its description and
save without reopening. Expect **Script changed. Reopen it before saving.**
Tab B's draft should remain in its editor. Copy any changes you want to keep
before reopening the current version.

## 7. Check execution failures and recovery

Use **New script** for these checks, so your saved example stays intact. You do
not need to save a draft to run it.

| Draft to run | Expected result |
| --- | --- |
| `return await tools.call('not_in_allowlist', {});` | An allowlist error; no connector call is dispatched. |
| `while (true) {}` | An execution/time-limit error within approximately five seconds, plus request overhead. |
| `return { process: typeof process, require: typeof require, fetch: typeof fetch };` | All three values are the string `"undefined"`. |
| `return 'x'.repeat(32769);` | An error because output exceeds 32 KiB. |
| Parameters `[]` rather than a JSON object | **Parameters must be a JSON object.** before execution. |
| `return { ok: true };` after a failure | A successful run, showing the runner recovered. Reset invalid parameters to `{}` first. |

Viewers can open and run saved scripts using their own permitted tools, but
cannot save or delete them. The PostgreSQL tests below check workspace isolation
using separate temporary tenant fixtures; the browser tests check viewer controls.

## 8. Run automated tests

Run these separately from manual testing. Stop the regular application with
**Ctrl+C** before Playwright: its Next server uses the same `.next` directory.
The standalone demo fixture can also be stopped; automated tests supply their
own connector fixture or mock responses.

Backend runtime, permission, and CRUD tests:

```bash

npm test -- --runInBand codebound
```

Expect **76 passing tests** and the PostgreSQL tests skipped by default.
Local HTTP fixture tests need permission to listen on localhost when run inside
a restricted coding-agent sandbox.

Include real PostgreSQL persistence, tenant isolation, concurrent writes, and
foreign-key checks:

```bash

set -a
. ../../.env
set +a
RUN_CODEBOUND_DB=1 npm test -- --runInBand codebound
```

Expect **81 passing tests**. These require the migrated local database at
localhost:5433 and create/remove their own temporary records.

Browser tests, with the regular dev server stopped:


Expect **7 passing Chromium tests**. Playwright starts Next on port **3100**;

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The sidebar has no Codebound entry | Use the checkout containing the local changes, restart `npm run dev`, and reload the browser. |
| Prisma reports a missing `codebound_scripts` table or stale client | Apply `prisma migrate deploy`, run `prisma generate` with the local `.env` exported, then restart the backend. |
| Prisma cannot reach PostgreSQL | Docker must be running; start the Compose `postgres` service and check that `DATABASE_URL` uses localhost:5433. |
| Save controls are absent | Sign in as an editor or administrator. |
| No tools appear | Check active server, active/ready connector, enabled tool, server assignment, REST read method, and your role's tool access. |
| The connector cannot reach 127.0.0.1:4100 | Keep the demo API running, check it with curl, and add 127.0.0.1 to the local `SSRF_ALLOWED_HOSTS` before restarting the app. |
| Save or Run reports that the script changed | Reopen the current version and review it before saving or running again. |
| The runner remains busy after a timeout | An already-started connector read can finish in the background; its run slot stays occupied until it finishes. |
| Playwright reports a Next.js lock | Stop the regular dev server before starting the port-3100 test server. |
| Email verification fails because SMTP is missing | Reuse your existing verified account, or configure working SMTP for registration/verification. |

The application feature behaves the same in Cloud and self-hosted deployments:
saved scripts are scoped to their workspace, and execution retains the caller's
tool permissions and existing license checks. The terminal, database, SMTP, and
loopback setup above is for local self-hosted development only.

To have an agent write and submit its own scripts, or to exercise execution and
save/reuse in Inspector, follow [AI-authored scripts through MCP](codebound-mcp.md).
The six Codebound tools are available on authenticated per-server and shared
connections. You can test them without manually creating a script per connector.

When finished, stop `npm run dev` and the local API with **Ctrl+C**. Keep the
PostgreSQL data volume so saved scripts remain available for the next session.
